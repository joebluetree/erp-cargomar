# Frontend Architecture

Implements the PRDs in `kb/platform/frontend.md` and `kb/platform/app-shell.md`. Code lives in `frontend/`. Setup commands are in `frontend/README.md`.

## Overview

A single Angular 22 application using standalone components (no NgModules), strict TypeScript and strict templates, zoneless change detection, and Spartan UI (on Tailwind CSS v4) as the UI library. It is organized by feature. It contains shared infrastructure (API access, errors, notifications, theme, shell) and one business feature, the Company List report (`features/reports/company-list`), which follows the conventions below.

Every page is displayed inside an application shell (header, sidebar menu, content area), and the Dashboard is the landing page.

Not implemented on purpose: authentication, user menu, route guards, breadcrumbs, nested menu groups.

## Project and folder structure

The Angular project sits directly in `frontend/` (`package.json`, `angular.json`, `src/` are direct children).

```
frontend/
  components.json            Spartan CLI config (where helm components are generated)
  .postcssrc.json            Tailwind CSS v4 PostCSS plugin
  proxy.conf.json            dev-server proxy: /api -> backend
  src/
    styles.css               Tailwind import and Spartan theme (CSS variables)
    environments/            environment.ts, environment.development.ts (apiBaseUrl)
    app/
      app.ts                 root component: router outlet and the toaster
      app.config.ts          providers: router, HttpClient + interceptors
      app.routes.ts          lazy routes
      core/
        api/                 API_BASE_URL token, apiBaseUrlInterceptor
        errors/              ApiError, toApiError, httpErrorInterceptor
        navigation/          NAV_ITEMS, NAV_ICONS and the NAV_MENU token: the single list behind the menu and Dashboard quick links
        notifications/       NotificationService
        theme/               ThemeService (light/dark)
      shell/                 Shell (header with theme switch, sidebar, sheet, content outlet) and AppNav (the menu)
      shared/
        ui/                  Spartan helm components generated by the CLI (only the ones in use; table and button carry the common look), page-title/ (PageTitle), table-toolbar/ (TableToolbar), table-wrap-toggle/ (TableWrapToggle) and icon-tone/ (AppIconTone, the named icon colors)
        paging/              Paged<T>, page sizes, rangeOf, TablePager (the footer every table uses) and TableStateStore
        testing/             look-guard (the check that screens do not set brand or table colors), the look-and-feel tests and their Node typings; excluded from the app build
      features/
        dashboard/           Dashboard landing page
        reports/company-list/  Company List report: model, sort helper, service, page, routes
        <area>/<feature>/    further business features are added here
```

## Boundary rules

- `features/*` may import from `core` and `shared`.
- `core` and `shared` never import from `features`.
- A feature never imports from another feature. There are no exceptions.
- Only a feature's service talks to the backend. Components and templates never contain URLs.

## Routing

`app.routes.ts` has one parent route whose component is `Shell`. Its children are the Dashboard at `''` and the lazy `loadChildren` routes of the features (today `reports/companies`); any unknown path redirects to `''`. There are no guards. Shell and menu are part of the initial download; the Dashboard and every feature are separate lazy chunks.

## Application shell

`Shell` (`app/shell`) is the frame around every page: a header (the app name "Cargomar Pvt Ltd", a link to the Dashboard with the same look as plain text, the hamburger buttons and the theme switch), a sidebar, and `<main class="page">` with the router outlet. It supplies the page width and padding, so feature pages render only their own content and do not add `<main>`. The content area fills the width beside the sidebar and starts at its left edge (`w-full min-w-0 flex-1 p-6`; no `mx-auto` and no `max-w-*`), on every page. The toaster stays in `App`, outside the shell. There is no user menu or breadcrumb.

### Menu

`core/navigation/nav-items.ts` exports `NAV_ITEMS`, a typed list of `{ label, icon, route, tone }` (currently Dashboard `/` and Company List `/reports/companies`), and `NAV_ICONS`, the Lucide icons those items name. Components read the list through the `NAV_MENU` injection token, which defaults to `NAV_ITEMS` and can be overridden in tests. `AppNav` renders the list as a `<nav aria-label="Main menu">` of router links and registers the icons with `provideIcons(NAV_ICONS)`. The current entry gets the `active` class through `routerLinkActive`; Dashboard (`/`) matches exactly, other entries also match pages beneath them (so a page at `/reports/new` highlights an entry for `/reports`). `AppNav` emits `navigated` when an entry is chosen.

### Responsive behavior

The header holds two hamburger buttons with the menu icon, and the 768px (Tailwind `md`) breakpoint, which is pure CSS, decides which one is visible. Below 768px the sidebar is hidden and `Open menu` (`md:hidden`) opens the same `AppNav` inside a Spartan `hlm-sheet` (left side). At 768px and wider the sidebar sits beside the content and the wide-screen button (`hidden md:inline-flex`, `aria-controls="sidebar"`) hides and shows it: it flips a `sidebarOpen` signal in `Shell`, the `<aside id="sidebar">` is `hidden md:block` while the signal is true and just `hidden` while it is false, and the content (`flex-1`) takes the freed width. The button's name states the action ("Hide navigation bar" / "Show navigation bar") and it sets `aria-expanded`. The signal lives in `Shell`, which stays alive across routes, so the choice survives moving between screens; it is not stored, so a browser reload shows the sidebar again. The sheet's state is a `menuOpen` signal in `Shell`, bound to the sheet's `state` input and `stateChanged` output: the narrow button opens it; choosing an entry (`navigated`) or dismissing the sheet (close button, Escape, overlay click) closes it.

### Theme (light and dark)

`core/theme/theme.service.ts` holds the theme as a signal (`'light' | 'dark'`) with `toggle()` and `set()`. The initial theme is the stored choice (`localStorage`, key `ierp-theme`), else the operating system's `prefers-color-scheme`, else light. The service applies the theme by toggling the `dark` class and the `color-scheme` style on `<html>`. Spartan's generated `:root.dark` variables in `styles.css` and Tailwind's `dark:` variant (`@custom-variant dark` in Spartan's preset) both key on that class, so every component follows it with no per-component code.

To avoid a flash of the wrong theme, a short inline script in `index.html` applies the same stored-else-system rule to `<html>` before the app starts. Keep the script and the service in sync. (A strict Content-Security-Policy would need to allow this script.) Storage access is wrapped in try/catch: if the browser blocks it, the switch still works for the visit but is not remembered.

The header button (`Shell`) shows the theme the user will switch to (moon in light mode, sun in dark mode) and its `aria-label` states the action ("Switch to dark theme" / "Switch to light theme"). Portal-rendered pieces (sheet, alert dialog) inherit the class from `<html>`. The Sonner toaster has its own theme input, so `App` binds it to the service: `<hlm-toaster [theme]="themeService.theme()" />`. In dark mode the text tokens (`--foreground`, card, popover, secondary, accent and sidebar foregrounds) are softened to `oklch(0.87 0 0)` instead of Spartan's near-white `0.985`: about 13:1 contrast on the page background (19:1 before), 12:1 on cards and 10:1 on secondary/accent surfaces, all above WCAG AA. Muted text stays at `0.708`, so it is still dimmer. To change the brightness, edit those values in the `:root.dark` block of `styles.css`. There is no "follow the system" option and no server-side preference.

### Adding a menu entry for a new module

1. Add the module's lazy route as a child in `app.routes.ts`.
2. Add one item to `NAV_ITEMS`: its label, its icon (added to `NAV_ICONS`), its route and an icon color `tone` (one of the named tones, see "Look and feel"; pick one no other entry uses).

The menu and the Dashboard quick links pick it up. The shell does not change.

## Dashboard

`features/dashboard` is the landing page. It shows a heading and a short welcome text, and a "Quick links" section built from the menu list (every entry except the Dashboard itself). While the menu has only the Dashboard, the quick-links section is not shown. The Dashboard shows no data and makes no backend requests, and it imports nothing from other features.

## Spartan UI and Tailwind

Spartan has two layers. `@spartan-ng/brain` is an npm package of unstyled, accessible primitives. `helm` is a set of Tailwind-styled components that the Spartan CLI generates as source into this project, which then owns them. There is no license key.

- Tailwind CSS v4 runs through `@tailwindcss/postcss` (`.postcssrc.json`). `src/styles.css` imports Tailwind and holds the theme (the neutral theme from `ng g @spartan-ng/cli:init`, with `--primary` changed to brand green, `oklch(0.48 0.11 150)` (about #246e3a, a toned-down green: white text 6.2:1, dark-mode title 3.2:1, so do not go duller without checking) with white `--primary-foreground`, in both themes; change the brand color there only; `--primary-surface` is the solid fill behind primary buttons and table headers, darker than `--primary` in both themes (light `oklch(0.42 0.09 150)`, about #225a31; dark `oklch(0.36 0.07 150)`, about #1e4729), so the fills are not glaring while titles keep `--primary`) as CSS variables.
- `components.json` sets the helm output folder to `src/app/shared/ui`. Components are imported through the `@spartan-ng/helm/<name>` path aliases in `tsconfig.json`.
- Generated so far, because the shell and the Company List use them: `button`, `sheet`, `sonner`, `table`, `input`, `label` (plus `utils`). The Company List uses a native `<select>` for the page size rather than the Spartan select, which keeps it simple and accessible. Add another with `npx ng g @spartan-ng/cli:ui <name>`; generate only what is used, and remove one that stops being used.
- Font: Roboto, self-hosted with `@fontsource/roboto` (weights 400, 500 and 700 imported in `styles.css`, so the font files are bundled with the app and nothing is requested from an external host). `--font-sans` in `styles.css` lists Roboto first with `sans-serif` and the emoji fonts as fallback; Tailwind and the Spartan components inherit it, and form controls inherit it through Tailwind's preflight. Change the font in that one variable.
- Icons are Lucide through `ng-icon` (`@ng-icons/lucide`); each component registers the icons it uses with `provideIcons`.
- Components are used directly, with Tailwind utility classes for layout. No wrappers. Spartan has no provider setup in `app.config.ts`.

## API integration

- `API_BASE_URL` (from `environment.apiBaseUrl`, default `/api`) is the single source of the backend address.
- `apiBaseUrlInterceptor` prefixes relative URLs with it, so services call `http.get('customers')`. Absolute URLs pass through untouched.
- In development the dev server proxies `/api` to the backend (`proxy.conf.json`), so there are no CORS problems. The backend has no CORS configuration; a deployment on a different origin needs it added.

## Interceptors

Two small functional interceptors, registered in this order in `app.config.ts`: `apiBaseUrlInterceptor`, then `httpErrorInterceptor`. They contain no feature logic and no authentication. Add new cross-cutting concerns as separate small interceptors.

## Notifications and error handling

- `NotificationService` (`success`, `info`, `warn`, `error`) wraps Spartan's Sonner `toast`. The single `hlm-toaster` in `app.ts` renders them. Toasts last 5 seconds and can be closed.
- `httpErrorInterceptor` converts every failed request to an `ApiError { status, message, fieldErrors? }` via `toApiError`, shows one error notification, and rethrows the `ApiError`.
- Messages are fixed, user-friendly texts: network failure (status 0), not found (404), generic (5xx and unknown). Backend exception text is never displayed.
- A 400 with an `errors` map is not notified. `fieldErrors` (keys converted to lower-camel, e.g. `Title` becomes `title`) go to the caller, which shows them next to the fields.
- Features do not notify about failures themselves; they only notify about success.

## Feature conventions

The Company List demonstrates these. Delete confirmation, forms and field-error handling are not exercised yet (the report is read-only); they remain the plan for the first feature that edits data.

- **State.** Feature services own state with signals, close to the feature, provided by the feature's routes (not `providedIn: 'root'`), with `load`, `save` and `remove` and readonly `items`, `loading` and `error` signals. No NgRx.
- **Forms.** Typed Reactive Forms (`FormBuilder.nonNullable`) built from the Spartan input, textarea, checkbox and label. A message shows under a field once it is touched; an invalid form marks every field touched and sends nothing; backend `fieldErrors` (already provided by the error interceptor) are set on the matching controls, and an error for an unknown field goes to a notification; Save is disabled while the request is in flight.
- **Data tables (every table, small or large).** The backend filters and pages; the browser never downloads a full list and filters or pages it. A table has a filter row with a **Search** button: typing changes nothing and sends nothing (no Enter key, no form), and pressing Search sends the filter values and shows page 1. The page keeps two things apart: what is typed (`codeInput`, `nameInput` signals) and the filters last searched (`applied`); paging and page-size changes always use the searched filters, never text typed since. Each Search, page change or page-size change is one request (`GET <endpoint>?<filters>&page=&pageSize=`) answered with `Paged<T>` (`items`, `total`, `page`, `pageSize`, in `shared/paging`). The feature service `load(query)` builds the query parameters (blank filters left out), keeps `items`, `total`, `loading` and `error` signals, and ignores a response that a newer `load()` superseded. The footer is always `TablePager` from `shared/paging`, with a thin separator (`<hr>`) directly above and below it, in one left-aligned wrapping row with `gap-x-10` between its three parts, in this order: rows shown out of the total; First/Previous/Next/Last icon buttons with "Page n of m" between Previous and Next; and, last, "Rows per page" (2/5/10/25/50/100); it only emits what the user chose). Sorting stays in the browser and reorders only the rows of the page on screen (`sortCompanies`, locale-aware, ignores case); rows keep the backend's order (name, then id) until a sort is chosen, so across pages the order is the backend's. The empty-state row says "no companies" when no filters were searched and "no match" when they were; a page past the end (empty items with a total that has rows) makes the page request the last page that has rows; a failed load shows an alert with a Retry button that repeats the same request (the interceptor shows the one notification). Sortable headers are buttons with `aria-sort` on the `<th>`, `hlmTableContainer` scrolls the table horizontally on narrow screens, and state is not kept in the URL. Delete asks for confirmation in a Spartan alert dialog before sending the request, then shows a success notification.
- **Generating components.** Generate the Spartan components a feature needs (`alert-dialog`, `textarea`, ...) with the CLI when that feature is built.
- **Back button.** A page that is reached from another page puts a ghost icon `Back` button (`lucideArrowLeft`, `aria-label="Back"`) before its `<h1>`, on the same row. It calls `Location.back()` when `Router.currentNavigation()?.previousNavigation` shows the user arrived from inside the app, otherwise it navigates to the Dashboard (`window.history.length` is not used: it also counts pages outside the app). It is local to the page; extract a shared component when a second page needs it.
- **State that outlives the screen (every table).** Feature services are route-provided and die with the route, and so do a page's own signals. A table must show the same filters, page, page size, sort and selection when the user leaves its screen and comes back, so it saves that state in the root-provided `TableStateStore` (`shared/paging/table-state.ts`: `get<T>(key)` / `set<T>(key, state)` over an in-memory `Map`), under its own key (the Company List uses `'reports/companies'`, exported as `COMPANY_LIST_STATE_KEY`). The page defines a snapshot type (`CompanyListState`: typed filter text, the filters last searched, page, page size, sort and whether a sort was chosen, and whether text wraps), reads it when it is created to initialise its signals, so its first request is for the remembered page with the remembered searched filters, and saves it again from an `effect` and once more when it is destroyed. Rows are never stored: they come from the backend each time, so the table shows current data, and a remembered page that no longer exists falls back to the last page that has rows. Typed-but-unsearched text is shown again but is not sent. The state is in memory only, so a browser reload clears it (no `sessionStorage`). The selected row is kept the same way by a small separate store (`CompanyListSelection`: the selected id, root-provided; rows are rendered selected when their id matches, so it survives paging, sorting and filtering, and a missing id highlights nothing). Rows are focusable (`tabindex="0"`), toggle on click, Enter and Space, and expose `aria-selected`.
- **Table look.** A table screen does not style itself. It uses `hlmTable`, `hlmTh`, `hlmTr`, `hlmTd` for the table, `<app-table-toolbar>` for the filter row and `<app-table-pager>` for the footer, and marks the selected row with `data-state="selected"`; the colors, stripes, column lines, 12px text, separators and spacing come from those pieces (see "Look and feel"). Page titles keep their normal case.
- **Feature service.** `CompanyListService` is provided by the feature routes (`providers` on the route), exposes readonly `items`, `loading` and `error` signals and a `load()` that ignores a response superseded by a newer `load()`. It does not notify about failures.

## Look and feel

One look for the whole application, defined once. A screen uses named pieces and never sets brand or table colors itself. The business requirements that every list screen must meet (the *what*) are in `kb/platform/list-screen.md` (`LS` rules); this section and the rest of this document are the *how*, and each list's own BRS says it follows `LS` and states only what is specific to it.

**1. Named theme values** (`src/styles.css`, light and dark):

| Value | Tailwind name | Meaning |
|---|---|---|
| `--primary`, `--primary-foreground` | `text-primary`, `text-primary-foreground` | brand green and the white text on it (titles, tints) |
| `--primary-surface` | `bg-primary-surface` | the solid green fill (primary buttons, table header); darker than the main green in both themes, darkest in the dark theme |
| `--table-header-bg`, `--table-header-fg`, `--table-header-line` | `bg-table-header`, `text-table-header-foreground`, `border-table-header-line` | table header fill, its text and its column lines |
| `--table-stripe`, `--table-selected`, `--table-line` | `bg-table-stripe`, `bg-table-selected`, `border-table-line` | alternating row, selected row, body column lines |

The table values are defined once in `:root` as references to the theme values above (for example the stripe is `--muted` at 50%), so the dark theme changes them without repeating them. To change the look, change the value there; every screen follows. Each value is mapped to a Tailwind name in the `@theme inline` block.

**2. Shared pieces** (use these, add nothing to the screen):

| Part | Piece | What the screen writes |
|---|---|---|
| Title | `PageTitle` directive (`shared/ui/page-title`) | `<h1 appPageTitle>` (layout classes only, such as `class="mb-4"`) |
| Navigation icons | `AppIconTone` directive (`shared/ui/icon-tone`) and the `--icon-<tone>` theme colors | `<ng-icon [name]="item.icon" [appIconTone]="item.tone" />` (the tone comes from `NAV_ITEMS`) |
| Buttons | the default variant of `hlmBtn` (`shared/ui/button`, project-owned source) | `<button hlmBtn>`; `variant="outline"`/`"ghost"` for secondary buttons |
| Table header | `hlmTh` defaults (`shared/ui/table`) | `<th hlmTh>` |
| Table rows | `hlmTr` and `hlmTd` defaults: stripe on even body rows, hover, selected color, focus ring, column lines, no line after the last column | `<tr hlmTr [attr.data-state]="selected ? 'selected' : null">`, `<td hlmTd>` |
| Table text | `hlmTable` default, 12px | `<table hlmTable aria-label="...">` |
| Filter row | `TableToolbar` (`shared/ui/table-toolbar`): separator, one wrapping row, separator | `<app-table-toolbar>` with each filter as a label beside its input, then the Search button |
| Wrap or scroll | `TableWrapToggle` (`shared/ui/table-wrap-toggle`) and the `group` / `data-wrap` support in the table container and cells | `<app-table-wrap-toggle [(wrap)]="wrap" />` directly above the table and `[attr.data-wrap]="wrap() ? 'true' : null"` on `<div hlmTableContainer>` |
| Footer | `TablePager` (`shared/paging`) | `<app-table-pager>` |

**Navigation icon colors.** Each `NAV_ITEMS` entry names a tone (`blue`, `green`, `amber`, `violet`, `rose`, `teal`; a seventh, `brand`, is `--icon-brand: var(--primary)`, the title green, and is what the header hamburger icons use); the six colors are defined in `styles.css` as `--icon-<tone>`, for the light theme in `:root` and, lighter, for the dark theme in `:root.dark`, all at least 3:1 (3.4:1 at the lowest) against the sidebar and its hover/active background. `AppIconTone` sets the icon component's own `--ng-icon__color` to `var(--icon-<tone>)` (a Tailwind `text-*` class could lose to the icon, which sets its color inside a CSS layer). `AppNav` (sidebar and slide-in menu) and the Dashboard quick links both use it, so an entry's icon has the same color everywhere, and it keeps that color when hovered or active. An entry without a tone shows the icon in the text color.

**Hand pointer.** One global rule in `styles.css` (`@layer base`, marked `clickable-cursor`) gives `cursor: pointer` to `button:not(:disabled)`, `[role='button']:not([aria-disabled='true'])`, `a[href]`, `select:not(:disabled)` and `summary`, so every button and link, present and future, shows the hand with no class, and a disabled button keeps the normal pointer. Selectable table rows are not buttons: the shared `hlmTr` adds `[&[tabindex]]:cursor-pointer` (a row is focusable only when the screen makes it clickable), so a screen writes no cursor class. `shared/testing/clickable-cursor.spec.ts` reads the rule's selector list out of `styles.css` and checks, with the DOM's own `matches`, that every enabled button, link and dropdown in the shell, the Dashboard and the Company List is covered and that disabled ones are not (jsdom loads no stylesheet, so it cannot read the computed cursor).

**Wrap or scroll.** The table container is a `group` that scrolls sideways (`overflow-x-auto`); header and body cells keep `whitespace-nowrap` and add `group-data-[wrap=true]:whitespace-normal group-data-[wrap=true]:wrap-anywhere`. A screen shows the shared "Wrap text: off|on" toggle (an outline button with `aria-pressed`, `secondary` when on) directly above the table and sets `data-wrap="true"` on the container while it is on: off keeps single-line cells with a horizontal scrollbar when the table is wider than the screen, on wraps the cells to the available width (`wrap-anywhere` lets long unbroken text such as an email address break). The toggle starts on (wrapping) and the choice is part of the screen's remembered state.

**3. Guard rails.** `shared/testing/look-guard.spec.ts` reads every template and code file under `src/app/features` (not the specs) and fails the build when one contains a literal color (palette names, hex, `rgb(`/`oklch(`) or a brand/table color class (`text-primary`, `bg-primary*`, `bg-muted*`, `bg-accent*`, `bg-table-*`, `border-table-*`, ...). `text-muted-foreground` (secondary text) and the neutral base classes (`bg-background`, `text-foreground`, `border-border`) are allowed. `shared/testing/look-and-feel.spec.ts` renders the shared pieces once and asserts the look, and reads `styles.css` to assert that each value is defined once and mapped, so screen tests do not repeat look checks (they only check that the screen uses the pieces, through `data-slot` attributes).

**Adding a new table screen:** use the pieces above, set `data-state="selected"` for a selected row, put filters in `<app-table-toolbar>`, end with `<app-table-pager>`, and write no color or size classes. **Changing the look:** edit the value in `styles.css` or the default in the shared piece, and run `npm test`; the shared test fails if a value is lost, and the guard fails if a screen starts styling itself. **A part that needs a new look value:** add a named value to `styles.css`, map it in `@theme inline`, use it only inside a shared piece, and extend `look-and-feel.spec.ts`.

## Shared UI components

`shared/ui` holds the generated Spartan helm components (the table and button carry the common look, see "Look and feel") and the look pieces `PageTitle` and `TableToolbar`. Other shared components are added only when a second feature genuinely needs one; keep them free of feature logic and prefer Spartan components directly.

## Testing

Angular's default runner (Vitest) via `npm test -- --no-watch`. No backend or browser needed.

- `toApiError` and the interceptors (`HttpTestingController`).
- `ThemeService`: default light, system preference, stored choice over system, invalid stored value, toggle and class, remembering across visits, blocked storage.
- `NAV_ITEMS`, `AppNav` (entries, links, active highlighting, exact Dashboard match, `navigated`) and `Shell` (header, menu, routed page, sheet opens and closes, theme button name and toggling) tests.
- Look and feel (`shared/testing`): the shared pieces' look asserted once, the named theme values, the check that screens set no brand or table colors (and the checker's own tests on bad samples), plus `PageTitle` and `TableToolbar` component tests.
- `Dashboard` component: heading and welcome text, no quick-links section for a Dashboard-only menu, links for extra menu entries (via the `NAV_MENU` token, with the real menu giving a Company List link), no backend requests.
- `rangeOf`, `TablePager` (range text, disabled moves, emitted pages and sizes) and `TableStateStore` (per-key get/set, a new application starts empty), and Company List: `sortCompanies`, `CompanyListService` (`HttpTestingController`: query parameters, blank filters left out, stale responses) and the page against a small fake backend that filters and pages like the API (Search is the only trigger, paging keeps the searched filters, sorting is local, empty/loading/error/retry, page past the end, remembered state after leaving and returning, accessibility hooks).

## Adding a feature

1. Add its entry to `NAV_ITEMS` and a lazy child route under the shell in `app.routes.ts`.
2. Create `features/<area>/<feature>/` with `<feature>.model.ts`, `<feature>.service.ts`, `<feature>.routes.ts`, and its pages.
3. Make the service own signal state and the backend calls with paths relative to the API base (for example `http.get('customers')`). Provide it in the feature routes.
4. Follow the conventions above: a typed Reactive Form, the Spartan table, `NotificationService` for success, and let the interceptor report failures. Generate any Spartan component you need with the CLI.
5. Pages render only their content (the shell supplies the page frame).
6. Add service and component tests (the interceptor and component tests in this project show the pattern).
7. Update this document if the feature changes a convention.
