# Design

## Context

See `proposal.md` for motivation and assumptions. This is the first business feature, so it also confirms the conventions in `kb/architecture/backend.md` and `kb/architecture/frontend.md`, which were written but never exercised.

- **Backend.** `Repository<T>` is Guid-keyed (`GetByIdAsync(Guid)`), `AppDbContext` has no `DbSet`s, and every migration so far manages tables this system owns. The target database is Oracle 10.2; `Oracle10gCompatibilityInterceptor` rewrites only a trailing `FETCH FIRST n ROWS ONLY`. Controllers must not depend on `iErp.Data`; modules reference Entities, Data, Shared and SharedBusiness only. `ModuleTemplate` is the skeleton to copy.
- **Data.** The BRS names the existing table `COMPANYM` with a string key (`COMP_PKID NVARCHAR(40)`), unlike the Guid/`RAW(16)` convention.
- **Frontend.** Zoneless Angular with signals, Spartan UI (only `button`, `sheet`, `sonner` generated), a single `NAV_ITEMS` list, lazy routes under `Shell`, and an HTTP error interceptor that already notifies on failures.

## Goals / Non-Goals

**Goals:**

- Ship the Company List end to end following the documented conventions, with as few exceptions as possible and each exception written down.
- Keep the table logic (filter, sort, page) pure and unit-testable without a browser or database.

**Non-Goals:**

- Server-side sorting, export, printing, or any company maintenance (that is the Admin module's `MAST_COMPANY`).
- Authentication, permissions, multi-company scoping of the list.
- A generic reusable data-table component. A second feature that needs the same table logic is the trigger to extract one.

## Decisions

**1. Read the existing `COMPANYM` table as a read-only, externally owned entity.**
`Company` (in `iErp.Entities`) has `Id` (string), `Type`, `Code`, `Name`, `Address1..3`, `Tel`, `Email`, `Web`, `DeletedDate`. The dev table (checked in task 1.1) also holds branches (`COMP_TYPE = 'B'`, 26 rows, each with `COMP_PARENT_ID`) next to companies (`'C'`, 4 rows), so the repository filters `Type == "C" && DeletedDate == null` (decided with the user: companies only; excluding soft-deleted rows is an assumption, 0 exist today). The real table has many more columns than the BRS; only the ones above are mapped. Real lengths differ from the BRS (`COMP_CODE` NVARCHAR2(10), `COMP_NAME` NVARCHAR2(60)); that is harmless for a read-only mapping. `CompanyConfiguration` (in `iErp.Data/Configurations`) maps it to `COMPANYM` and its explicit upper-case columns, with `HasKey(Id)` and `ToTable("COMPANYM", t => t.ExcludeFromMigrations())`, so migrations never create, alter or drop it. A new migration is therefore not needed, and the model snapshot is regenerated only if EF requires it. Alternatives: *create the table by migration* (rejected: it already exists and holds data in the target database; a migration would fail or fight it); *keyless entity/`FromSql`* (rejected: a keyed read-only entity needs no raw SQL and keeps `AsNoTracking` queries simple).
`Id` is a string, so it does not fit `Repository<T>.GetByIdAsync(Guid)`. The list needs no lookup by key, so `CompanyRepository` is a small class that depends on `AppDbContext` and exposes only `ListAsync`-style reads; it does not derive from `Repository<T>`. This is the one exception to the Guid-key convention; it is limited to this legacy table and recorded in `kb/architecture/backend.md`.

**2. One paged endpoint following a shared contract.**
`GET /api/reports/companies?code=&name=&page=&pageSize=` (`CompaniesController` in `iErp.Reports/CompanyList`) binds a `CompanyListQuery` (class with defaults: `Page` 1, `PageSize` 10) from the query string. A `CompanyListQueryValidator` (FluentValidation, picked up by the existing `ValidationFilter`) rejects `page` < 1, a `pageSize` outside 2/5/10/25/50/100 and filters longer than 60 characters with the usual grouped 400. `ICompanyListService.ListAsync(query)` calls the repository and maps to `PagedResult<CompanyListItemDto>` (manual mapping, null to empty string).
The contract is shared so every table looks the same ("everywhere"): `iErp.Shared/Paging` holds `PagedResult<T>(Items, Total, Page, PageSize)` and `PagingRules` (allowed sizes, default size, default page). `iErp.Data` cannot reference Shared (dependency rules), so its helper `ToPageAsync(page, pageSize, ct)` on `IQueryable<T>` takes plain ints and returns the rows and the total; the module combines them into the `PagedResult`.
The repository filters with case-insensitive contains (`c.Code.ToUpper().Contains(code.ToUpper())`, which Oracle EF translates to `INSTR(UPPER(col), :p) > 0`). `INSTR` is also what makes `%` and `_` literal characters, where `LIKE` would need escaping. Blank filters are not applied. The query orders by name and then by id (`COMP_PKID`) so pages never overlap or skip when names repeat, and uses `AsNoTracking`. Total is a `CountAsync` over the same filtered query.
**Paging on Oracle 10.2.** EF Core's `Skip/Take` produces `OFFSET n ROWS FETCH NEXT m ROWS ONLY`, which 10.2 does not have. `ForPage` uses plain `Skip(offset).Take(size)`. Checked against the real 10.2 database (the probe in task 3.13): the provider sends them as bind parameters, `OFFSET :p_0 ROWS FETCH NEXT :p_1 ROWS ONLY`, and when offset and size are equal EF shares one bind (`:p_0` twice), so the rewrite must accept bind names as well as numbers (an earlier idea of forcing literals with `EF.Constant` does not work: it cannot be called outside a query lambda, and constants are parameterised anyway). `Oracle10gCompatibilityInterceptor` gains a second rewrite next to the existing `FETCH FIRST` one: a trailing `OFFSET a ROWS FETCH NEXT b ROWS ONLY` becomes `SELECT * FROM (SELECT "t".*, ROWNUM "RN__" FROM (<query>) "t" WHERE ROWNUM <= a + b) WHERE "RN__" > a`, repeating the same bind names (the provider binds by name, so a name may appear several times). The extra `RN__` column is the last column, which EF ignores because it reads by ordinal. `ToPageAsync` skips the page query when the total is 0 or the page is past the end. Alternatives: *raw SQL for each table* (rejected: every module would repeat it); *keyset paging* (rejected: arbitrary jump to the last page and page numbers are required); *client-side paging* (rejected by the requirement: backend paging everywhere).

**3. New module `iErp.Reports`, copied from `ModuleTemplate`'s shape.**
A class library with the same references, one registration method `AddReports` (registers the service and repository and its validators from the module assembly) and a feature folder `CompanyList/`. `Program.cs` calls `AddReports()` and adds the assembly as an application part; `iErp.Api.csproj` and `iErp.sln` reference it. `ModuleTemplate` stays untouched as the skeleton. The architecture tests' module list is extended so the dependency rules (no Api, no other module, controllers not using `iErp.Data`, no test code) run against both assemblies. This is why `backend-solution-structure` is modified (the "seven projects" wording).

**4. Shared paging pieces; the page keeps typed text apart from the applied filters.**
`shared/paging/` (importable by every feature) holds `Paged<T>`, `PAGE_SIZES`, `DEFAULT_PAGE_SIZE`, a pure `rangeOf(total, page, pageSize)` (page count, from, to) and the `TablePager` component (range text, page size select, First/Previous/Next/Last icon buttons with the same names as before and the page number, "Page n of m", in its own element between Previous and Next so the range text is untouched; inputs `total`, `page`, `pageSize`; outputs `pageChange`, `pageSizeChange`). It is shared now because the requirement is that every table uses the same pager. A thin `<hr>` sits directly above and below the footer row (inside the pager, so every table gets them; the top one carries the gap to the table, the row has vertical padding). Its footer is one wrapping flex row, left-aligned (`justify-start`, no `justify-between`), with `gap-x-10` between its three parts (range text, page buttons, then the "Rows per page" choice last) and `gap-3` between the buttons, so it reads left to right with room between the parts.
`features/reports/company-list/` contains:

- `company-list.model.ts`: `Company`, `CompanyListQuery` (`code`, `name`, `page`, `pageSize`), `SortColumn`, `SortState`, `COLUMNS`, `DEFAULT_SORT`.
- `company-list.table.ts`: the pure `sortCompanies` only (sorts the rows of the shown page, case-insensitive, stable). The client-side `applyFilters` and `pageOf` are removed.
- `company-list.service.ts`: provided by the feature routes; `load(query)` sends `http.get<Paged<Company>>('reports/companies', { params })` (blank filters omitted) and exposes readonly `items`, `total`, `loading`, `error` signals; it ignores a response that a newer `load()` superseded. It does not notify (the interceptor does).
- `company-list.page.ts/html`: signals `codeInput` and `nameInput` (what is typed), `applied` (the filters that were last searched), `page`, `pageSize` and `sort`. The Search button (`type="button"`, no form, so Enter does nothing) copies the inputs to `applied`, sets `page` to 1 and calls `load`. Paging and page size call `load` with `applied` (never the typed text). Sorting only changes the `sort` signal and re-sorts the shown rows. The empty-state message is chosen from `applied` (no filters: "no companies"; filters: "no match"). If a response is empty while `total` > 0 and `page` > 1, the page requests the last page that has rows. Retry repeats the last query.
- `company-list.routes.ts`: provides the service and the page at `''`; `app.routes.ts` mounts it lazily at `reports/companies`.

Alternatives: *a generic data-table component that owns filters too* (rejected: filter fields differ per table, only the pager and the contract are common); *an `effect` that reloads when signals change* (rejected: it would make typing search, and the requirement is that only Search does).

**4a. Back button (local to the page).** An icon button (`hlmBtn` icon variant, `lucideArrowLeft`, `aria-label="Back"`) sits in a flex row immediately before the `<h1>`. It returns to the page the user came from with the `Location` service: `location.back()` when the user arrived by navigating inside the application, otherwise `router.navigateByUrl('/')` (Dashboard). "Arrived inside the application" is read from the router's navigation state (`router.currentNavigation()` / `history.state.navigationId > 1`), not from `window.history.length`, which also counts pages outside the app. No shared component: this is the only page with a back button; extract one when a second page needs it. Alternative: always navigate to a fixed page (rejected: the user asked for the page it came from).

**4b. Layout and colors.** The filters become inline label-plus-input pairs (`flex items-center gap-2` per pair, pairs in a wrapping row), with a styled horizontal rule above and below the filter row (an element with `role="separator"`, border color from the theme; no Spartan separator is generated). The header row gets the theme `muted` background; body rows alternate between the default background and a lighter `muted`; the selected row uses a tint of the theme `primary` color (`bg-primary/15`). `accent` is not used because this theme gives `accent` and `muted` the same value, which would make the selected row look like the header; the `primary` tint differs from the header, both stripes and the hover color in light and dark mode. Body rows are plain `<tr>` elements with their own classes rather than `hlmTr`, because `hlmTr` bakes in its own hover and selected colors (`muted`). All colors are theme tokens, so both themes follow without per-theme code. Column separators are a right border on every header and body cell except the last in its row (`border-r ... last:border-r-0`): `border-primary-foreground/30` (a light line) on the colored header and `border-border` in the body, so they follow the theme too. Table text is 12px: `text-xs` is set once on the `<table>`, overriding Spartan's default `text-sm`, and the header and body cells inherit it (the sort arrows are 12px to match). The footer and the filters keep the page's 14px. Paging gains `lucideChevronsLeft` and `lucideChevronsRight` as first-page and last-page icon buttons around Previous and Next (`aria-label`s "First page", "Last page").

**4c. Row selection store.** The selected company id lives in `CompanyListSelection` (`company-list.selection.ts`), a small in-memory store with a `selectedId` signal and `toggle(id)`. It is provided in root, unlike `CompanyListService` (route-provided and destroyed with the route), because the selection must outlive the route; it is lost on a browser reload, as required, and needs no browser storage. The page renders a row as selected when `selectedId()` equals the row's `id`, so a selection survives paging, filtering and sorting (the id is independent of the row's position), a row hidden by a filter stays selected, and an id that is no longer in the loaded list simply highlights nothing (no explicit cleanup). Rows get `tabindex="0"`, `aria-selected`, and click plus Enter/Space handlers. The rest of the page state is kept the same way, through a generic store (decision 4e); the selection stays in its own small store because it is already built and tested, and could be folded into the saved state later. Alternatives: *`sessionStorage`* (rejected: survives reload, which is not wanted); *keep the route alive with a route-reuse strategy* (rejected: global behavior, and it would also keep stale rows).

**4d. Page width and alignment (shell-owned).** The frame belongs to the shell, so the fix is there, not in the page: the `<main class="page">` in `shell.html` loses `mx-auto max-w-5xl` and keeps `w-full min-w-0 flex-1 p-6`, so the content starts at the left of the content area and fills the width beside the sidebar. This applies to every page (the Dashboard too); the `app-shell` capability is modified for it. The table is already `w-full` inside a container that scrolls sideways, so it spans the wider area on large screens and still scrolls on narrow ones. Alternative: override the width only on the Company List (rejected: the app-shell spec says feature pages do not provide their own frame, so a per-page override would be an exception to it).

**4e. State that outlives the screen (every table).** `shared/paging/table-state.ts` holds `TableStateStore`, root-provided, with `get<T>(key)` and `set<T>(key, state)` over an in-memory `Map`. It knows nothing about any table; each table page uses its own key (the Company List uses `'reports/companies'`), so tables never share state. The Company List defines a `CompanyListState` snapshot in `company-list.model.ts`: `codeInput`, `nameInput`, `applied`, `page`, `pageSize`, `sort`, `sortChosen`. The page reads the snapshot in its constructor (if there is none, the defaults apply), initialises its signals from it, and its first `fetch()` therefore sends the remembered query. One `effect` writes the current snapshot back to the store whenever any of those signals changes. Rows are never stored: the restored query is sent to the backend each time, so the table shows current data, and the existing past-the-end effect handles a remembered page that no longer exists. Memory only, so a browser reload clears it, as required. Alternatives: *`sessionStorage`* (rejected: survives reload); *a store per feature* (rejected: the user wants this for every table); *caching the rows too* (rejected: stale data, and the backend is the source of truth).

**4f. Brand color (app-wide, one definition).** The theme's `--primary` is the brand green (`oklch(0.48 0.11 150)`, about `#246e3a`) with white `--primary-foreground`, in `:root` and `:root.dark` alike. The color was blue first, then a vivid green (`oklch(0.527 0.154 150.069)`, `#008236`), then toned down at the user's request (lower lightness and much lower chroma); each change was a one-line edit, which is the point of defining it once. A separate lighter green with dark text was tried for the dark theme (task 3.31) and put back at the user's request (task 3.32), so both themes use this one value again. Measured contrast: white text on it is 6.2:1 (the vivid green gave 4.9:1) and the 24px title in it is 3.2:1 against the dark page background (large text needs 3:1; the vivid green gave 4.0:1). That is the limit: a duller or darker green drops the dark-mode title below 3:1, so go no further without lightening the title in dark mode. Everything that already used `primary` follows (default buttons such as Search, and the selected-row tint `bg-primary/15`). Page titles get `text-primary` (Company List, Dashboard) and the table header cells `bg-primary text-primary-foreground`. **Fills vs. text (task 3.33).** Dimming the whole dark-mode green would also dim the title, which is already at 3.2:1, so the solid backgrounds use a second theme color, `--primary-surface` (Tailwind `bg-primary-surface`, mapped in an `@theme inline` block in `styles.css`): its own darker green in each theme (light `oklch(0.42 0.09 150)`, about `#225a31`, white text 8.1:1; dark `oklch(0.36 0.07 150)`, about `#1e4729`, white text 10.5:1; first it equalled `--primary` in the light theme and was `oklch(0.42 0.09 150)` in the dark theme, and was lowered in task 3.40 because both looked too bright). The default button variant of the generated Spartan button (`hlm-button.ts`, project-owned source) and the table header cells use it; titles and the selected-row tint keep `--primary`. A solid header is used rather than a light tint so it stays clearly different from the selected row, which is a light primary tint, and from the neutral stripes. Alternatives: *override only on this page* (rejected: the user chose an app-wide theme); *a separate `--table-header` token* (rejected: not needed while the header follows the main color).

**4g. Common look and feel (named values plus shared pieces).** The look is split into three layers so that no screen styles itself.
1. *Named theme values* in `styles.css`: `--table-header-bg`, `--table-header-fg`, `--table-header-line`, `--table-stripe`, `--table-selected`, `--table-line` (next to `--primary`, `--primary-surface`, `--primary-foreground`), defined once in `:root` as references to the existing theme values (for example the stripe is `--muted` at 50%, the selected row `--primary` at 15%), so they follow `:root.dark` automatically and look exactly as they do now. An `@theme inline` block maps them to Tailwind colors (`bg-table-header`, `text-table-header-foreground`, `border-table-header-line`, `bg-table-stripe`, `bg-table-selected`, `border-table-line`).
2. *Shared pieces in `shared/ui`* (project-owned source, the Spartan way): the generated table directives carry the look as their defaults: `hlmTable` is 12px; `hlmTh` has the header fill, text and column line; `hlmTd` has the padding and column line; `hlmTr` has the stripe on even body rows (`even:not-data-[state=selected]:bg-table-stripe`), the hover, the selected color from `data-state="selected"` and the focus ring; both cells drop the line on the last column. The page therefore writes `<th hlmTh>` and `<tr hlmTr [attr.data-state]="...">` and nothing else about color. A `PageTitle` directive (`appPageTitle`, selector `[appPageTitle]`) holds the title style (size, weight, `text-primary`). A `TableToolbar` component holds the two separators and the wrapping row, with the filters and Search button projected into it. Buttons already get the look from the default variant of `hlm-button.ts`; the footer from `TablePager`.
3. *A check*: a unit test reads the feature templates and code (`src/app/features/**`, not specs) and fails when one contains a literal color or one of the brand or table color classes (`text-primary`, `bg-primary*`, `bg-muted*`, `bg-accent*`, `bg-table-*`, `text-table-*`, `border-table-*`, palette colors, hex colors); `text-muted-foreground` stays allowed for secondary text. A second test renders the shared pieces once and asserts the look (header, stripes, selected, hover, lines, text size), so these facts are no longer repeated in every page's tests.
The selected row uses an attribute (`data-state`) rather than a class so the look decides what selected means. `even:` selects the second, fourth... row of the body, which are the same rows the page striped before (index 1, 3...). Alternatives: *one config-driven data-table component* (rejected: filters, columns and row actions differ per screen, so it would be rigid and grow flags); *keep classes in each page and document them* (rejected: they drift, which is the problem); *Tailwind `@apply` classes in `styles.css`* (rejected: Spartan's directives are already the place where the project owns component styles).

*How 4b and 4f read now:* they describe the values and the reasons (the dimmer dark fill, the primary tint for the selected row, the stripes, the column lines, the 12px text). Since 4g those values are applied by the shared pieces through named theme values, not by classes on the Company List page: the header is `bg-table-header` (= `--primary-surface`), the header line `border-table-header-line` (= `--primary-foreground` at 30%), the stripe `bg-table-stripe` (= `--muted` at 50%), the selected row `bg-table-selected` (= `--primary` at 15%), the body line `border-table-line` (= `--border`). The result is the same as before, and nothing on the page sets them.

**4h. Wrap or scroll (shared).** The shared table pieces get a second mode, driven by one attribute. `HlmTableContainer` gains the `group` class; `hlmTh` and `hlmTd` keep `whitespace-nowrap` and add `group-data-[wrap=true]:whitespace-normal group-data-[wrap=true]:wrap-anywhere`, so a screen turns wrapping on by putting `data-wrap="true"` on the container (`[attr.data-wrap]="wrap() ? 'true' : null"`) and writes no classes. The container keeps `overflow-x-auto`, so with wrapping off the table scrolls as before, and with wrapping on it simply fits. `wrap-anywhere` (`overflow-wrap: anywhere`) is used instead of `break-words` because it also lets the browser shrink the column's minimum width, which a long email address would otherwise keep wide. The toggle is a shared `TableWrapToggle` component (`shared/ui/table-wrap-toggle`): a `model` boolean `wrap` and a button with `aria-pressed`, the label "Wrap text: off|on" (the state is in the text, not only in a color) and an icon that changes, `secondary` variant when on and outline when off. It sits left-aligned directly above the table. The default is on (it was off first and was changed at the user's request, task 3.44): the toggle's `model` starts `true` and the Company List's `wrap` signal starts `true`. The Company List saves the signal in its remembered state (`CompanyListState.wrap`, optional so older saved state means the default, on). Alternatives: *wrap always* (rejected: the user wants to choose, and wide tables are easier to scan single-line); *a toggle in the filter toolbar* (rejected: it is about the table, not the filters); *a per-column setting* (rejected: not asked for).

**4i. Colored navigation icons (named tones).** Each menu entry names a tone (`NavItem.tone`: `blue`, `green`, `amber`, `violet`, `rose` or `teal`; Dashboard is `blue`, Company List `green`), and a small shared directive `appIconTone` (`shared/ui/icon-tone`) turns the tone into the icon's color by setting the icon component's own CSS variable, `--ng-icon__color`, to `var(--icon-<tone>)` through a host style binding. The CSS variable route is used instead of a Tailwind `text-*` class because the icon component sets its color inside a CSS layer and a utility class could lose to it. The six tone colors are named values in `styles.css`, defined for the light theme in `:root` and for the dark theme in `:root.dark` (raw colors, since a dark page needs lighter icons: for example green `#1d7d3e` in light and `#5bbd74` in dark), and all are at least 3.4:1 against the sidebar and the hover/active background in both themes. `AppNav` (sidebar and slide-in menu, one component) and the Dashboard quick links both write `[appIconTone]="item.tone"`, so there is one mapping and no color class in any screen (the look guard still passes). The tone lives next to the icon in `NAV_ITEMS`, so a new menu entry picks a tone in the same line that picks its icon; an entry without a tone shows the icon in the text color. Alternatives: *all icons in the brand green* (rejected: the user chose a color per item); *a color class per item written in the nav component* (rejected: it would put color classes in a screen and would not be shared with the Dashboard).

**4j. Header name and hamburger.** The header caption becomes "Cargomar Pvt Ltd" (the Dashboard welcome text and the browser tab title keep "iErp" for now; they were not part of the request). The hamburger is pure CSS at the existing 768px breakpoint, so there is no width check in code: two icon buttons sit at the start of the header, `Open menu` (`md:hidden`, opens the slide-in sheet as before) and a new wide-screen toggle (`hidden md:inline-flex`), both with the menu icon, so exactly one is visible at any width. The toggle flips a `sidebarOpen` signal in `Shell` (default shown); the `<aside id="sidebar">` stays `hidden md:block` while the signal is true and is just `hidden` while it is false, so the content (`flex-1`) takes the freed width. The signal lives in `Shell`, which stays alive across routes, so the choice survives navigation and is gone after a reload (no storage). The toggle's name states the action ("Hide navigation bar" / "Show navigation bar") like the theme button does, with `aria-expanded` and `aria-controls="sidebar"`. Alternatives: *one button that checks the width in code* (rejected: needs `matchMedia`, which the test environment lacks, and the breakpoint is otherwise CSS only); *remember the choice in `localStorage`* (rejected: not asked for; the theme is stored because it is a preference, this is a layout state); *animate the collapse* (rejected: not asked for).

**4k. Hamburger color (the `brand` tone).** The header hamburger icons use the existing icon mechanism (`appIconTone`) with a seventh tone, `brand`, defined as `--icon-brand: var(--primary)` in `:root` only: it is the title green by reference, so it follows any change to the main green and is not repeated in the dark block (the six palette tones keep their own lighter dark values; the theme test treats `brand` separately). Setting the icon component's color variable rather than a text class means the ghost button's `hover:text-foreground` cannot recolor the icon. Contrast of the icon green against the header: 6.2:1 in the light theme and 3.2:1 in the dark theme, which meets the 3:1 minimum for graphics; it is the same dull green the dark-mode titles use, so it shares their limit. Alternatives: *a `text-primary` class on the buttons* (rejected: hover recolors it, and a color class would sit in the shell template); *a lighter green for the dark theme* (rejected: the user asked for the brand green, and a separate dark green for the title was tried and reverted).

**4l. Hand pointer on everything clickable (one global rule).** Tailwind's base styles give buttons the plain arrow, and only the selectable table rows had a `cursor-pointer` class on the page. One rule in `styles.css` (`@layer base`, after the Tailwind imports, marked `clickable-cursor`) sets `cursor: pointer` on `button:not(:disabled)`, `[role='button']:not([aria-disabled='true'])`, `a[href]`, `select:not(:disabled)` and `summary`, so every present and future button and link has it with no class, and a disabled button keeps the normal pointer. Icons inside a button inherit the cursor. Selectable table rows are not buttons, so the shared `hlmTr` gets `[&[tabindex]]:cursor-pointer` (a row is focusable only when the screen makes it clickable) and the Company List loses its own `cursor-pointer` class. The tests read the selector list out of `styles.css` and check, with the DOM's own `matches`, that every enabled button, link and dropdown rendered by the shell, the Dashboard and the Company List is covered and that disabled buttons are not; they cannot check the computed cursor because the test environment loads no stylesheet. Alternatives: *`cursor-pointer` on `hlmBtn` and on each link* (rejected: misses plain buttons such as the sort buttons and any future one); *a directive on every clickable thing* (rejected: easy to forget, which is the problem).

**4m. The header name is a link to the Dashboard.** The caption in the shell header is an `<a routerLink="/">` with the same classes it had as a span (`text-xl font-bold`), so it looks the same: links inherit the text color and have no underline in the base styles. Because it is a real link it is keyboard focusable, announced as a link with the name "Cargomar Pvt Ltd" (a `title` of "Go to the Dashboard" adds a tooltip without changing the accessible name), and the global hand-pointer rule for `a[href]` covers it with no class. It uses the router, not a full page load, so the shell, the remembered table state and the sidebar choice stay as they are. Clicking it on the Dashboard stays on the Dashboard. Alternatives: *a button that navigates in code* (rejected: not a link, so no open-in-new-tab or hover address); *only the logo area as a link* (rejected: there is no logo).

**5. Menu entry.** `NAV_ITEMS` gets `{ label: 'Company List', icon: 'lucideFileText', route: '/reports/companies' }` (the label was "Reports" first and was changed at the user's request, task 3.45; the Dashboard quick link uses the same label) and `NAV_ICONS` the icon. The shell's prefix matching highlights the entry for the page and the Dashboard quick links list it automatically (the existing "dashboard shows no quick links" test, which relies on the menu being Dashboard-only, is adjusted to use the `NAV_MENU` override).

## Risks / Trade-offs

- **A remembered page or filter can surprise a user who expects a fresh list** → Accepted: it is what the user asked for, a browser reload resets it, and the filter boxes always show what is applied.
- **A remembered page may no longer exist** → The existing past-the-end rule requests the last page that has rows.

- **Very wide screens make the Dashboard's short text sit far left in a wide area** → Accepted: the Dashboard has little content; a width cap can be re-added per page later if a text-heavy page needs one.

- **Selected color vs. stripes in dark mode** → Use distinct theme tokens (a `primary` tint vs `muted`) and check both themes in the integration pass.
- **Root-provided selection store is a deliberate exception to "feature services are route-provided"** → Document it in `kb/architecture/frontend.md`; it holds one id and no data.
- **Stale selected id after the list changes** → Harmless by design (highlights nothing); it is overwritten on the next selection.

- **`COMPANYM` is missing or differs from the BRS in the target database** → The first integration run against the real schema reveals it; the mapping uses explicit column names, so a mismatch fails with a clear Oracle error, and the first task verifies the table before coding.
- **`ExcludeFromMigrations` still lets EF write the entity into the model snapshot** → That is expected; the snapshot records the model but the generated migration has no DDL for the table. Task: generate a migration, confirm it is empty for `COMPANYM` and delete it (or do not add one if EF reports no model change).
- **Nullable columns vs. non-nullable C# strings** → Entity properties are declared nullable-aware and the DTO mapping normalizes `null` to `""`, so a sparse legacy row cannot break the list.
- **The `OFFSET`/`FETCH` to `ROWNUM` rewrite is regex-based on provider-generated SQL** → The pattern only needs the trailing clause, which has been checked against the real 10.2 database; unit tests cover the rewrite, and the Oracle-gated test pages a real table on 10.2. A provider upgrade that changes the SQL shape fails those tests rather than the app.
- **Every page and every search costs a count query plus a page query** → Accepted for the requirement of backend paging; both are indexed-friendly filters on a small table.
- **Duplicate or divergent company data once the Admin module's `MAST_COMPANY` exists** → Out of scope here; flagged in the proposal so the data-source decision is revisited with that module.
- **Sorting only reorders the shown page** → Chosen by the user. It is stated in the spec; the backend order (name ascending, then id) is the order across pages. Server-side sorting would be a follow-up that adds `sort` and `direction` to the shared contract.

## Migration Plan

No schema change and no data migration. Deploy backend and frontend together (the page needs the endpoint). Rollback is redeploying the previous build; nothing is written to the database.
